# 작업 보고서 2026-11-25: Gaia DR4 전환 준비 (2.60.6, 과제 1)

계획 세션 지시서(2026-11-25 과제 1)에 따라 DR4 전환의 **준비**만 했다. DR4 자료는 보지 못했고(공개 2026-12-02), 전환과 짝 비교는 하지 않았다. DR3 결과는 같다.

## 1. 한 일과 결과
- 문서 둘: `GAIA_DR4_READINESS_2026-11-25.md`(의존 목록 42항목, 잠근 프로토콜, 코드 준비), `LITERATURE_GAIA_DR4_2026-11-25.md`(DR4 조사, 확인 수준 표시).
- DR4 데이터 모델 초안(ESA가 2026-06-26 공개한 ZIP의 PDF, 1,231쪽)을 내려받아 구문 분석했다: 표 141개, 열 4,629개(`benchmark/gaia_dr4/dr4_draft_tables.json`). DR3 수집기가 요청하는 64열 대조(`dr3_columns_vs_dr4_draft.csv`): 같은 표에 남는 것 35열(`gaia_source` 27 + `vari_summary` 8), **다른 표로 간 것 20열(천체물리)**, **초안에 없는 것 7열**.
- 코드: 제품 지도(`gaia_release.py`), 분류 상수 표(`Preprocess/gaia_assumptions.py`), `check_gaia_release.py` DR4 발견 모드, 시험 11개.
- DR3 동일성: 시험 + 같은 원자료 4곳 × 5개 파일을 2.60.3 코드와 모든 셀 비교(다른 셀 0).

## 2. 왜 이렇게 짰나
- **제품 지도.** 기존 `gaia_release.py`는 스키마 이름과 기준 시기만 가졌고 열 목록은 `gaia_dr3.py`의 상수였다. DR4는 천체물리 표가 4개로 나뉘고 열 일부가 없어서, DR3 목록을 DR4 표에 보내면 ADQL 오류다. 릴리스마다 `{제품 → (표, 열, 상태 열)}`를 갖게 하고 수집기는 그 지도를 순서대로 돌게 했다. DR3 지도는 옛 상수 그대로(열 목록 해시와 SQL 문자열을 시험이 묶음). DR4 지도는 **추측해 채우지 않고 `None`**으로 두었다: 초안은 초안일 뿐이라 아카이브 자신의 메타데이터를 읽은 뒤(`check_gaia_release.py`) 손으로 채운다. DR4를 고르면 DR3 사본으로 가서 DR3로 표시한다(아카이브가 죽었을 때와 같은 경로라 새 동작이 아니다).
- **분류 상수 표를 Preprocess 쪽에 따로.** 수집 쪽 `gaia_release.py`에 합치지 않았다: 단계 모듈들이 서로를 경로로 불러 쓰는 구조(Get_data와 Preprocess는 서로 import하지 않음)를 깨지 않기 위해서다. 두 표의 릴리스 이름이 같음은 시험이 확인한다. 릴리스는 환경 변수가 아니라 **데이터의 `gaia_release` 열**로 고른다: 저장된 DR3 원자료를 `V2_GAIA_RELEASE=DR4`인 환경에서 분류해도 DR3 값을 쓴다. 열이 없으면 DR3(보존된 특징, 옛 원자료).
- **DR4는 `LookupError`.** 값이 없는 릴리스의 행을 DR3 상수로 조용히 분류하면 영점이나 C* 판정이 틀려도 경고 없이 라벨이 바뀐다. 멈추는 편이 낫다.
- **`dataclass`에 `from __future__ import annotations`를 안 쓴 이유.** 단계 모듈들이 이 파일을 경로로 읽으면서 `sys.modules`에 등록하지 않아서, 문자열 주석의 dataclass가 `NoneType.__dict__` 오류를 냈다(시험 중 발견).
- **옮기지 않은 것.** `Classifier/branches/star.py`, `subclass.py`의 RUWE 1.4와 C* 식은 Classifier가 Preprocess를 경로로 읽지 않아 복사본이 남았다. 시험이 `star.py`의 식이 표의 DR3 값과 같음을 묶는다. 전환 때 같이 옮긴다.
- **대안으로 버린 것:** DR4 열 이름 대응을 지금 코드로 박는 것(초안에서 "같은 이름"인 열도 정의가 같다는 보장이 없고, 변광 분류기는 구조가 달라 대응이 설계 결정이다).

## 3. 확인하지 못한 것(미확인)
- DR3 표가 DR4 공개 뒤에도 같은 아카이브에서 제공되는지(어느 ESA 페이지에도 없음). DR4 TAP 스키마 이름. 시차 영점 레시피와 `ruwe`·오차의 DR4 정의(논문 목록에 있으나 arXiv 링크가 비어 있음). VizieR의 DR4 사본.
- DSC 논문(arXiv:2605.23388)과 FLAME 논문(arXiv:2607.00264)은 앞 40k자만 원문으로 읽었고 나머지는 요약이다. 해당 문장은 문서에 "요약만"으로 표시했다.
- 데이터 모델의 `tentative_parallax_bias`가 가리키는 참고문헌은 초안에서 `?`로 비어 있다.

## 4. 프로토콜의 숫자
채택 기준(정확도 차이 95 % 하한 ≥ −0.10 %p, 고신뢰 순도 84 % 하한 ≥ 0.98, 수집 시간 +20 % 이내 등)은 DR4 자료를 보기 전에 정한 **제안값**이다. 검토 세션이 바꾸려면 12-02 이전에 바꿔야 의미가 있다.

## 5. 병합 전 검토 (코드 개발 세션)

판 번호는 병합 순서에 따라 2.60.6이 됐다. 2.60.4는 12장 덱, 2.60.5는 세트 C 기록이다. 문서와 코드의 "2.60.4" 표기는 모두 2.60.6으로 바꿨다.

### 5.1 직접 확인한 것
- **DR3 결과가 같은지.** 로컬 1차 분류 벤치마크(`validate_catalog_truth.py` → `evaluate_rule_baseline.py`, 보존 특징)를 main(f1f38dd)과 이 브랜치에서 돌렸다. 출력 두 파일(`rule_baseline_metrics.json`, `rule_baseline_test_predictions.csv`)이 **바이트까지 같다**.
- **속도.** 평가 시간은 122.6 s와 122.7 s로 같다. 행마다 `GA.for_values([...])`를 부르지만 사전 조회 한 번이라 비용이 보이지 않는다.
- **시험.** 330개 통과.
- **DR4를 고르면 DR3로 돌아가는 동작이 사용자에게 보이는지.** 보인다. 행에는 `gaia_base_query_status = vizier_fallback`이 적히고, `catalog_coverage.ALTERNATIVE`(2.57.0)가 경고 띠와 `run_archives_missing`에 "Gaia from the VizieR I/355 copy"를 띄운다. 다만 그 문구에는 DR4를 요청했다는 말이 없어서 아래처럼 한 줄을 더했다.

### 5.2 고친 것
- **`gaia_dr3.fetch`:** 요청한 릴리스가 DR3가 아닌데 사본이 답하면 실행 기록에 `[gaia_dr3] Gaia DR4 was requested; answered by the VizieR DR3 copy, labelled DR3 (이유)`를 찍는다(컨트롤러의 `[수집기] …` 형식). 기존 시험에 이 줄을 확인하는 단언을 더했다. 경고 띠 문구까지 바꾸는 대안은 버렸다. `catalog_coverage`가 수집기의 요청 릴리스를 알아야 해서 범위가 커지고, 행의 `gaia_release = DR3` 표시와 경고 띠만으로도 조용히 넘어가지는 않기 때문이다.
- **`check_gaia_release.py --release DR4`:** 표마다 "초안이 약속했는데 없는 열 / 초안에 없던 열" 목록을 앞 12개까지만 찍던 것을 전부 찍게 했다. 이 출력이 프로토콜 (가)의 첫 점검 기록으로 커밋되므로 잘리면 안 된다.
  - 예: `phot_bp_rp_excess_factor`가 정식 공개에 생기면 "초안에 없던 열"에 나와야 한다. 그 열은 "DR3 열 → DR4 표" 목록(64열 전부)에도 나온다. `tentative_parallax_bias`는 스키마를 찾는 표지로 따로 찍는다.
  - 따라서 초안 기준의 두 판단(천체별 시차 보정, excess factor 부재)은 12-02 첫 점검이 그대로 다시 확인한다.
- **`check_gaia_release.py --release DR4`의 기준 시기 확인(Codex 지적, PR #82).** DR4 경로는 아카이브의 `ref_epoch`를 찍기만 하고, 질의가 실패하거나 `gaia_release.py`의 2017.5와 달라도 점검이 통과했다. 이전 점검과 DR3 경로는 둘 다 실패로 처리한다.
  - 수집기는 아카이브 값이 아니라 `gaia_release.py`의 시기를 모든 행에 적고, Stage 1은 그 값으로 고유운동을 전파한다. 그래서 틀린 시기가 점검을 통과하면 위치 연관이 조용히 틀린다.
  - 두 경우 모두 실패로 바꾸고 가짜 아카이브로 시험을 더했다(같음 → 통과, 2016.0 → 실패, 질의 실패 → 실패). 고치기 전 코드에서 이 시험이 실패함을 확인했다.
- **프로토콜 (라) 세트 C:** 원래는 세트 C가 (나)에 쓰이지 않는다는 말만 있었고, 이번에 보존한 블라인드 입력(2.60.4, 90일)과 어떻게 맞물리는지가 없었다. 이렇게 정했다.
  - 전환 뒤 한 번의 채점은 그 입력에서 Gaia 파일만 DR4 원뿔(같은 중심·반지름)로 바꿔 분류하고, 전환 전 기준 채점(2.60.4, `locked_c/2.60.4/`)과 묶음별 집계로 비교한다.
  - DR4에서 `source_id`가 바뀌어도 천체 짝은 만들지 않는다. 세트 C는 천체별로 보지 않기 때문이다(규칙 2·5). 연관은 Stage 1이 위치와 각 행의 `ref_epoch`로 다시 하고(`01_source_association.py`가 고유운동을 `ref_epoch`로 전파함을 확인), 정답 대조도 위치로 한다.
  - 아티팩트가 만료됐으면 새로 수집하고, 아카이브 날 효과가 섞였다고 적는다.
- **프로토콜 (마) DR3 경로:** 사본으로 오래 머물 때 약해지는 판정을 코드에서 찾아 적었다.
  - 1차 규칙은 사본이 비우는 18열을 읽지 않는다. 1차 라벨 차이는 26,024개 중 6개였다(`WORK_REPORT_2026-11-24.md`).
  - 약해지는 것은 세 가지다. 플럭스 오차가 없어 백색왜성 궤적 확률의 색 오차가 0이 되고(`star.py`), compact 축의 `in_vari_compact_companion`과 extragalactic 축의 `in_vari_agn`이 빠진다.

### 5.3 그대로 둔 것
- **(다)의 문턱.** 제안값 그대로 잠갔다. −0.10 %p 하한은 32,814개 기준 약 33개로, 지금까지 관측한 변형 간 차이(+0.01, −0.02 – −0.03 %p)보다 넉넉하면서도 엄격하다.
  - r > 22 GALAXY 순도 하한 0.98은 2.60.2 측정값(0.983, 84 % 하한 0.982)의 바로 아래다. 그래서 DR4가 이 값을 조금만 떨어뜨려도 걸린다. 이것은 의도한 엄격함으로 읽었다.
  - 문턱을 DR4를 보기 전에 정한다는 원칙을 지키려고 숫자는 바꾸지 않았다.
- **Classifier 쪽 RUWE·C* 복사본(`star.py`, `subclass.py`).** 작업 세션의 판단대로 전환 때 옮긴다. 지금은 시험이 DR3 값과 같음을 묶는다.
