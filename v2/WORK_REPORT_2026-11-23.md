## 2. SkyServer 오류 페이지 (지적 1)

### 재현
- 넘겨받은 재현 명령(`m.fetch(188.4155, 9.1751, 2)`)은 이 컨테이너에서 **성공**했다(1행). 대신 COSMOS 2′가 "결정적으로" 실패했다. 실패하는 영역이 환경마다 다르다는 것이 첫 단서였다.
- 같은 요청을 astroquery 캐시 없이 보내면 성공하고, 캐시를 켜면 실패했다. 캐시 폴더(`~/.cache/astropy/astroquery/FullPrecisionSDSS/`)에 HTTP 200으로 저장된 1,379바이트 HTML이 있었다.
  - 내용: `<title>Skyserver Error</title> … 403 - Forbidden: Access is denied.` (고정본 `Preprocess/tests/fixtures/skyserver_error_403.html`)
  - 이것을 CSV로 읽으면 넘겨받은 그 오류("Number of header columns (1) inconsistent with data columns in data line 9")가 난다.
- 빈도: 처음에는 같은 요청 약 40번 중 1번. 한 시간쯤 뒤에는 같은 측광 원뿔 12번(4초 간격) 중 4번. 서버 쪽 상태에 따라 달라진다(부하 분산 뒤의 서버 하나가 거절하는 것으로 보이지만 확인하지 못했다).
- astroquery는 200 응답을 요청 해시로 일주일 저장한다. 그래서 한 번 받은 오류 페이지가 **같은 원뿔·같은 열 목록의 모든 조회에 재생**된다. "11월 15·17·18일 같은 영역에서 실패"와 맞는다.
- 2.55.0 기준 실행에서 SDSS **측광**(`sdss_dr18`)도 같은 페이지로 실패했다(COSMOS, 은하면). 이 수집기는 실패하면 운동 열 없이 다시 묻는데, 그 재질의까지 오류 페이지였다.

### 고침과 이유
- `_catalog_utils._sdss()`의 클라이언트가 `_request`를 감싼다: 오류 페이지면 캐시 항목을 지우고, 캐시 없이 다시 묻는다(1초 간격, 모두 5번). 끝까지 오류면 `SkyServerError`로 서버 문구를 그대로 올린다.
- `sdss_spectroscopy._sql`(선 질의)도 이 클라이언트를 쓴다. 전에는 astroquery 기본 객체를 써서 보호가 없었다.
- 5번인 이유: 측정한 최악 비율(1/3)에서 5번 모두 실패할 확률이 0.4 %다. 2번 재시도(3.7 %)로는 부족했다. 요청마다 3–5초 대기 규칙이 따로 걸리므로 추가 대기는 1초면 된다.
- 404 페이지(너무 긴 GET, 3절)는 다시 물어도 같으므로 재시도하지 않는다.
- 버린 대안
  - **SDSS 요청에서 astroquery 캐시를 끄기:** 오염은 막지만 일시적 403은 그대로 실패한다. 열 목록 검증용 메타데이터 요청(128 KB + 52 KB)도 매번 다시 받게 된다.
  - **질의를 나누거나 형식 바꾸기(넘겨받은 제안):** 원인이 질의가 아니라 서버의 간헐 응답이라 효과가 없다.
- 한계: 다른 astroquery 수집기(VizieR 등)도 200으로 온 오류 본문을 캐시할 수 있다. 이번에는 관측된 SDSS만 고쳤다.

## 3. EW 오차 조회 (지적 3)

### 원인
- SkyServer SQL 검색은 GET이다. URL 2,073자는 답했고 2,123자는 `404 - File or directory not found`였다(IIS 질의 문자열 기본 한도 2,048자).
- 2.55.0은 id를 80개씩 보냈다. 18자리(SDSS-I/II) id면 넘지 않지만 19–20자리(BOSS) id면 넘는다.
  - MPA-JHU 질의: 오차 열이 없어도 80개에서 404(2,123자). **2.53.0 이전부터 있던 문제**로, BOSS 은하가 많은 영역은 Dn4000과 MPA-JHU 선을 잃었다.
  - Portsmouth 질의: 2.53.0이 오차 열 2개를 더하면서 한도에 걸렸다. 그러면 "retry without EW errors"로 넘어가 **그 영역의 모든 은하가 오차를 잃는다.**
- 은하가 한두 개인 영역(NGC 4522 2′, COSMOS 2′)에서는 오차가 정상으로 온다. 검토 세션이 COSMOS에서 본 재시도는 2절의 오류 페이지였을 가능성이 높다(같은 `InconsistentTableError`).

### 고침
- `_chunks`: 인코딩된 질의가 1,800자를 넘지 않게 id를 묶는다(URL 앞부분과 `format=csv`를 더해 2,000자 미만). 20자리 id면 약 62개, 18자리면 약 70개.
- 버린 대안: 묶음 크기를 60으로 줄이기. 열을 더하면 다시 넘는다. 길이로 묶으면 열 목록이 바뀌어도 맞는다.

### 측정 (`benchmark/measure_sdss_ew_errors.py`)
세부 분류 벤치마크(`evaluate_subclass.py`)는 SDSS 분광 열을 정답으로 쓰므로 분류기에 주지 않는다. 그래서 SDSS 선 판정은 SDSS×DESI 겹침 벤치마크(`desi_lines_truth/overlap.csv.gz`, 3,489개)의 분광을 수집기(`_lines`)로 다시 받아 쟀다. 2.53.0은 이 규칙을 DESI 선으로만 쟀다.

| | 2.55.0 묶음(80개) | 2.56.0 |
|---|---|---|
| 선 질의 상태 | `error:mpa_jhu` 3,489 | `ok` 3,489 |
| Hα EW 있는 은하 | 2,603 | 2,625 |
| 그중 EW 오차 있음 | **0** | **2,623** |
| 선 출처 Portsmouth / MPA-JHU | 2,609 / 0 | 2,609 / 16 |
| EW 1–5 Å 중 3 Å에서 2σ 안 | 0 / 462 | 183 / 467 (39 %) |

오차를 넣었을 때 선 판정 변화(2.56.0 자료, 같은 은하):

| 판정 | 오차 없이 | 오차 넣고 |
|---|---|---|
| QUIESCENT | 1,110 | 944 |
| STAR_FORMING | 999 | 989 |
| COMPOSITE | 379 | 359 |
| AGN | 122 | 88 |

- 230개가 보류로 바뀌었다(은퇴 166, AGN 34, 복합 20, 별 생성 10). DESI에서 잰 값(1,738개 중 102개, 5.9 %)과 비슷한 비율이다(6.6 %).
- 즉 2.53.0의 WHAN 오차 규칙은 SDSS 쪽에서 은하가 많은 영역이면 **작동하지 않고 있었고**, 이제 작동한다. 규칙 자체는 바꾸지 않았다.
- 오차 표는 `desi_lines_truth/sdss_ew_errors.csv.gz`에 두어 `--offline`으로 다시 셀 수 있다.

## 4. 실패 기억의 범위 (지적 2)

### 설계
`archive_cache.recent_failure(name, ra, dec, radius)`가 실패를 다음 경우에만 돌려준다.
1. **같은 원뿔**(위치 0.36″, 반경 같음)에서 실패했으면 언제나.
2. 다른 원뿔이면, 그 실패가 **시간 초과**였거나 10분 안에 **서로 다른 두 원뿔**에서 실패했을 때.
3. 그 수집기가 한 번 성공하면 기억을 모두 지운다.

### 이유
- 2.55.0이 이 기능으로 없앤 것은 "답하지 않는 서비스를 기다리는 시간"이다(ATNF·NED·LS, 검색당 60–300 s). 그 대기는 상태가 `timeout`인 실패에서 나온다. 그래서 시간 초과는 전처럼 모든 영역에 적용해 2.55.0의 이득을 그대로 둔다.
- 빨리 끝나는 `error`(해석 실패 등)는 다른 영역에서 한 번 더 물어도 비용이 요청 하나다. 대신 그 영역의 근거를 잃지 않는다.
- 빠른 오류로 나타나는 장애(오류 페이지를 곧바로 돌려주는 서버)는 두 번째 영역도 실패하므로 세 번째 영역부터 건너뛴다.
- 버린 대안: **예외 종류로 "연결 실패"와 "해석 실패"를 나누기(넘겨받은 두 번째 안).** 장애는 해석 오류로도 나타난다. 이번 SkyServer 403이 그랬고(HTTP 200 + HTML), 유지보수 중인 Gaia 아카이브도 HTML을 돌려줘 VOTable 해석 오류가 된다. 예외 종류는 장애와 질의 문제를 가르지 못한다.
- 2.55.0이 쓴 `failures.json`(이름 → 실패 하나)은 위치 없는 실패로 읽어 전체 적용한다(10분 뒤 사라짐).
- 핵심 수집기(Gaia, LS, PS1, AllWISE, 2MASS)의 처리는 그대로다(늘 다시 묻고, LS만 대기 90 s).

## 5. Gaia 수집 시간 (지적 4)

### 원인
- `gaia_dr3.fetch`는 TAP 작업을 네 번 한다: 기본 표, 천체물리 변수, 변광 분류, 변광 요약. 모두 **비동기** 작업이었다.
- 비동기 작업 하나는 요청 3–4개(제출, 상태 조회, 결과)이고, 요청마다 3–5초 대기 규칙(2.33.0, `throttle.py`)이 걸린다. Gaia TAP 클라이언트는 `http.client`를 써서 `V2_HTTP_LOG`에는 보이지 않는다.
- 같은 2′ 원뿔 기본 질의: 비동기 12.6 s, 동기 4.9 s. 네 작업 + 충실도(GAVO) = 55–64 s. 영역 크기와 거의 무관한 이유다.
- 로그의 "breaking changes"와 별개로, 아카이브는 **11월 25일부터 DR4 준비로 내려가고 12월 2일 DR4가 공개된다**는 안내를 낸다. 이 작업 도중(11월 23일)에도 유지보수 페이지로 바뀌었다.

### 고침
- `_tap`이 동기 요청을 먼저 보낸다. 동기 응답은 2,000행에서 잘리므로, 꽉 찬 응답과 실패는 전처럼 비동기로 다시 묻는다.
- 두 경로의 행 순서가 달라서 결과를 `source_id`로 정렬한다(어느 경로가 답했는지에 출력이 의존하지 않게).
- 버린 대안
  - **네 표를 LEFT JOIN 한 질의로:** 서버에서 40.6 s(동기) / 50.9 s(비동기) 걸렸다. 더 느리다.
  - **선택 표 세 개를 동시에 요청:** 빠르지만 요청 간격 규칙의 취지(아카이브 부하)에 어긋난다.
  - **대기 규칙 완화:** 프로젝트 규칙이라 건드리지 않았다.
- 대가: 2,000개 넘는 밀집 영역은 동기 요청 한 번(약 5 s)을 더 쓴 뒤 비동기로 간다.

### 측정 (수집기 단독, 캐시 끔, 아카이브 정상일 때)

| 영역 | Gaia 행 | 2.55.0 | 2.56.0 | 값 비교 |
|---|---|---|---|---|
| NGC 4522 2′ | 13 | 64.2 s | 32.2 s | 81열 모두 같음 |
| COSMOS 2′ | 9 | 59.8 s | 26.7 s | 같음 |
| 은하면 1′ | 254 | 58.6 s | 28.9 s | 같음 |

값 비교는 저장된 CSV를 `source_id`로 정렬해 맞춘 것이다. 다섯 가지 조회 상태 열도 모두 같았다(tap / ok).

## 6. 세 영역 전후 (전체 파이프라인)

같은 날 차례로 돌렸다(각각 새 캐시, `V2_HTTP_LOG=1`). **이 표의 시간 차이는 대부분 아카이브 상태 차이이고 코드 효과로 읽으면 안 된다.** 이날은 VizieR 스트라스부르가 404였고, 기준 실행 중 Legacy Surveys가 느렸으며(COSMOS 221 s), 수정본 실행 중 Gaia 아카이브가 유지보수로 내려가 VizieR 대체 경로를 탔다. 코드 효과만 떼어 잰 값은 5절(Gaia)과 2–3절(SDSS)이다.

| 영역 | | 전체 | 수집 | 천체 | Gaia | SDSS 분광 | SDSS 측광 | 실패 |
|---|---|---|---|---|---|---|---|---|
| NGC 4522 | 2.55.0 | 219 s | 212 s | 149 | 60 s / 13행 (TAP) | ok 1 | ok 92 | 없음 |
| | 2.56.0 | 132 s | 125 s | 149 | 121 s / 13행 (VizieR 대체) | ok 1 | ok 92 | 없음 |
| COSMOS | 2.55.0 | 273 s | 227 s | 994 | 62 s / 9행 (TAP) | ok 1 | **error**(403 페이지) | sdss_dr18 |
| | 2.56.0 | 146 s | 104 s | 1,001 | 76 s / 9행 (VizieR 대체) | ok 1 | ok 74 | 없음 |
| 은하면 | 2.55.0 | 181 s | 176 s | 591 | 118 s / 254행 (TAP, 선택 표 실패) | 0행 | **error**(403 페이지) | sdss_dr18 |
| | 2.56.0 | 81 s | 77 s | 591 | 73 s / 254행 (VizieR 대체) | 0행 | 0행 | 없음 |

1차 분류 라벨
- **같은 원자료, 새 코드:** 2.55.0의 은하면 원자료를 2.56.0으로 다시 분류 → 591개 모두 라벨 같음, p_star 차이 0. 분류 코드를 바꾸지 않았으므로 당연한 결과이고, 확인만 했다.
- **두 실행 사이:** NGC 4522 149개 0개 변화. COSMOS 대응된 992개 0개 변화(SDSS 측광 74행이 돌아오며 천체 수 994 → 1,001). 은하면 4개가 UNKNOWN → STAR.
  - 은하면 4개의 원인은 코드가 아니라 Gaia 자료다. 기준 실행에서는 아카이브가 내려가는 중이라 선택 표 세 개가 실패해(`gaia_ap_query_status = error:RuntimeError`) DSC 확률이 없었고, 수정본 실행은 VizieR 대체 경로에서 DSC를 받았다(세 천체 DSC star 0.994–0.999).
- 잠근 세트 C: 1차 분류 코드를 바꾸지 않아 채점하지 않았다.

## 10. X선 규칙 표본 (`benchmark/xray_rules/`)

- 새 수집기 없이 지금 받는 목록(4XMM-DR13, eRASS1, CSC 2.0, Gaia DR3, 2MASS)을 썼다. 정답 목록과 X선 목록은 VizieR 미러에서 통째로 받아 로컬에서 맞췄다. Gaia 아카이브가 DR4 준비로 중단이라 Gaia DR3·2MASS는 GAVO TAP(`gaia.dr3lite`, `twomass.data`) 업로드 교차 매칭으로 붙였다(VizieR 다중 위치 질의는 30개에 2분이라 쓸 수 없었다).
- 강착 천체 정답: CV(Ritter & Kolb) 1,429, HMXB(Neumann+2023, Fortin+2023) 190, LMXB(Avakyan+2023, Fortin+2024) 451. 3″ 안 중복 367개는 한 번만.
- 별 대조군 두 가지
  - **SDSS DR18 분광 별**(CV·WD 아형 제외): 스펙트럼으로 정한 별이라 X선/광학 비와 독립. X선 대응이 있는 1,343개.
  - **HamStar 코로나 별**(요청 대조군): 25,779개(4XMM·CSC 대응 전부 + eRASS1 전용 2만 개 무작위) 중 강착 천체 정답 3″ 안의 80개를 뺀 25,699개(SDSS 대조군과 같은 처리; 15절). 위 순환 때문에 따로 보고.
- AGN: SDSS DR18 분광 QSO(Lin 규칙의 "별" 판정 오염원).
- **우연 일치가 큰 함정이었다.** SDSS 별은 어둡고 고위도라 X선 오차원 안에 관계없는 AGN이 흔하다. 위치를 1–2′ 옮겨 다시 맞추면 대응의 19 %(4XMM, 3σ 최대 10″), 65 %(eRASS1), 11 %(CSC)가 그대로 남는다. 처음 잰 SDSS 별 오탐률(4XMM 35 %, eRASS1 72 %)은 대부분 이것이었다. 1.5″ 안으로 좁히면 우연 일치는 4.2 %(4XMM), 1.7 %(CSC)다. eRASS1은 위치 오차(~5″) 때문에 SDSS 별 대조군에 쓸 수 없다.

### 실제 하늘 정밀도
표본 안의 "순도"는 정답과 대조군 수의 비율에 달려 의미가 없다. 그래서 Rodriguez 표본을 재현했다: 4XMM 점광원 × Gaia DR3(GAVO, 3σ ≤ 3″) 188,485개 중 은하 조건 41,760개, 선 위 1,283개(3.1 %; 원문 25,050개 중 2.2 %). 정답 목록의 강착 천체는 이 중 59개이고 44개(75 %)가 선 위다(위 완전도와 같음).
- 별 오탐률을 HamStar 값 0.6 %(3σ, 0.4–1.0 %)로 두면(순환으로 낮게 편향): 기대 거짓 양성 ≈ 250(160–400), **정밀도 ≈ 0.80(0.69–0.88)이 상한**. (검토 전 1.2 %·0.62는 HamStar 대조군에 강착 천체 정답이 섞여 있던 값; 15절.)
- SDSS 분광 별 값 7.1 %(하한 3.8 %)로 두면 기대 거짓 양성(1,600–3,000)이 선 위 전체(1,283)를 넘는다. 이 대조군은 어둡고 먼 별이라 Rodriguez 표본보다 오탐이 많다고 봐야 하지만, 적어도 실제 정밀도가 0.80보다 높다고 볼 근거는 없다.

### 판단: 넣지 않음
- `Classifier/axes/compact.py`의 기존 규칙은 하늘 수준 사전확률 × 측정 우도비로 확신도를 정한다(예: 전파 펄서 후보). 같은 방식으로 이 규칙의 확신도는 **최대 ~0.8**(순환으로 유리한 대조군)이고, X선과 독립인 SDSS 별 대조군으로는 그보다 훨씬 낮다. "강착 천체"라는 판정(`INFERRED`)을 이 정밀도로 붙이면 선 위 천체의 적어도 5분의 1, 독립 대조군 기준으로는 대부분이 틀린 판정이 된다.
- HMXB 완전도 39 %, 은하 조건 밖 사용 불가(QSO 99 % 오탐)도 걸린다.
- 다음에 쓸 수 있는 형태: 판정이 아니라 "강착 천체 후보" 표지(분광 확인 권고). 이번 범위 밖이라 하지 않았다.

검토·계획 세션의 요청으로 이 브랜치를 검토하고 아래를 더해 병합했다.

### 실패 기억: 오래 걸린 오류도 모든 영역에
- **걱정:** 새 조건("시간 초과이거나 두 영역에서 실패")만 두면, 오래 걸려서 끝난 **오류**는 한 영역에만 기억된다. 예로 2026-11-17 HEASARC는 "System overloaded"를 66 s 뒤에 냈다. 그러면 다음 영역이 같은 대기를 한 번 더 치른다. 2.55.0이 없앤 것이 바로 이 대기다.
- **고침:** 실패에 걸린 시간(`seconds`)을 함께 저장한다. `SLOW_FAILURE_S` = 30 s 이상 걸린 실패는 시간 초과처럼 모든 영역에 적용한다(`archive_cache.recent_failure`).
- **그대로인 것:** 빠른 해석 오류(SkyServer 오류 페이지 하나 등)는 여전히 다음 영역에서 요청 하나만 더 쓴다.
- **시험:** `test_a_slow_error_is_remembered_for_every_cone`
- **Legacy Surveys:** 핵심 수집기라 기억과 무관하게 늘 다시 묻는다. 최근 실패 뒤 시도 1회(90 s) 처리는 그대로다(`recent_failure`를 위치 없이 부르므로 영역과 무관하게 적용).
- **ATNF:** HEASARC가 실패해도 30 s 뒤 VizieR 사본으로 성공하므로 기억에 남지 않는다.

### SkyServer 재시도의 대기
- 오류 페이지가 계속 오는 장애에서 질의 하나는 요청 5번(각 3–5 s 간격과 응답)과 대기 1 s × 4로 약 25–30 s다. 수집기 제한(300 s) 안에 든다.
- 위 규칙으로 이런 실패(≥ 30 s)는 다른 영역에도 적용되므로, 장애 중 다음 검색은 기다리지 않는다.

### WHAN 오차 규칙의 정밀도 (보고서 3절 보충)
같은 은하의 DESI 분광(`desi_lines_truth/overlap.csv.gz`)으로 낸 선 판정을 독립 기준으로 두고, SDSS 선 판정이 그것과 일치하는 비율을 쟀다. DESI EW 오차는 `halpha_ew_ivar`에서 구했다.

| SDSS 선 판정 | 판정 비율 (3,489개) | DESI와 일치 (둘 다 판정) |
|---|---|---|
| 오차 없이 (2.55.0 실제 동작) | 74.8 % | 81.8 % (n = 2,135) |
| 오차 넣고 (2.56.0) | 68.2 % | 82.4 % (n = 1,952) |
| 보류로 바뀐 230개의 이전 판정 | – | 76.0 % (DESI가 판정한 183개) |

- 판정 비율은 6.6 %p 줄고 일치율은 0.6 %p 오른다.
- 보류된 것은 평균보다 덜 맞던 판정이다(76.0 % 대 81.8 %). 대부분 "은퇴"(166개)였고, DESI는 그중 123개를 같은 판정, 38개를 보류로 냈다.
- 규칙이 의도대로 작동한다.

### X선 규칙 시험 고침 (PR #72 Codex 검토)
측정 스크립트의 결함 세 가지를 고치고 `xray_rules/metrics.json`을 다시 만들었다(11–12절 표는 고친 뒤 값). 판단(둘 다 넣지 않음)은 그대로다.
- **표본 내보내기 열 이름:** `build_sample.py`는 2MASS 열을 소문자(`t_kmag`)로 pickle에 남기는데 평가 스크립트는 `sample.csv.gz`의 `t_Kmag`를 읽는다. 저장소의 `sample.csv.gz`는 손으로 바꿔 만든 것이라, 스크립트만으로는 재현이 끊겨 있었다. `build_sample.py`가 평가 스크립트가 읽는 이름으로 `sample.csv.gz`를 직접 쓰게 했다.
- **HamStar 대조군의 강착 천체:** SDSS 대조군은 강착 천체 정답 3″ 안을 뺐지만 HamStar 대조군은 빼지 않아, 같은 천체(예: V2400 Oph, PSR B1259−63)를 맞게 잡은 것이 대조군 오탐으로 세어졌다. 80개를 뺐다(평가 스크립트 `drop_hamstar_compact`, `build_sample.py`에도 같은 처리).
  - Rodriguez HamStar 오탐 37/3,031 = 1.2 % → 18/3,002 = 0.6 %(3σ), 28/2,332 → 12/2,306(1.5″). 강착 천체 완전도는 그대로(117/157, 101/135).
  - 실제 하늘 정밀도 상한 0.62 → 0.80. 이 값도 HamStar의 순환 때문에 높게 잡힌 상한이고, X선과 독립인 SDSS 별 대조군(7.1 %)으로는 기대 오탐이 선 위 전체를 넘으므로 판단은 같다.
- **Ks 상한:** 2MASS ph_qual의 Ks 자리가 'U'이면 Ks는 측정이 아니라 상한이다. log(F_X/F_IR)를 아래로만 묶으므로 "< −0.9"(별)를 정할 수 없다. 이런 X선 쌍성 5개가 별로 세어지고 있었다. Lin 규칙에서 뺐다(빠진 수는 `metrics.json`의 `ks_upper_limits_left_out`).
  - SDSS 분광 별 0.764 → 0.775(1.5″), X선 쌍성 22–31 % → 22–32 %, QSO 1.9 %로 같음.
- **왜 판단이 그대로인가:** Rodriguez는 독립 대조군 기준 정밀도가 여전히 낮고 HMXB 완전도 39 %·은하 조건 밖 QSO 99 % 오탐이 남는다. Lin은 X선 쌍성의 약 30 %를 별로 부르는 것이 그대로다.
