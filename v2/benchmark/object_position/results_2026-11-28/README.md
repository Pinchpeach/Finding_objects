# 과제 버: `V2_OBJECT_POSITION=best`의 측정 (깊은 COSMOS 26개 영역, 전체 파이프라인 두 번)

예측은 `../PREDICTIONS_2026-11-28.md`(구현 전에 커밋 487b612, 첫 실행 뒤의 추가는 843dab9). 설계와 문헌은 `../../../LITERATURE_OBJECT_POSITION_2026-11-28.md`, 하류 좌표 사용처는 `../DOWNSTREAM_USE.md`. 이 폴더의 표는 `../run_pipeline_both.sh` + `../run_measure.sh`가 만든다(영역마다 스위치 끔·켬 전체 파이프라인 → 슬림 결과만 남기고 작업 폴더 삭제 → 합산).

규칙(최종): 구성원 중 **순위 오차**가 가장 작은 행 하나의 좌표를 출력 좌표로 한다. 순위 오차 = `max(poserr, 0.02″, PSF/6)`(연관의 유효 오차, 고유운동 항 없이), **Pan-STARRS1은 바닥 0.6″**; 같으면 바닥 밑의 측정 오차, 목록 우선순위(Gaia, LS, PS1, SDSS, 2MASS, AllWISE, GALEX, SIMBAD, NED), 목록 이름, 검출 id.

## 1. 라벨은 바뀌지 않는다 (설계의 핵심 조건)

`invariance.csv`: 26개 영역 모두 `classified_objects.csv`에서 **`ra`·`dec` 두 열만** 다르고(새 열 6개는 스위치를 켠 쪽에만), 라벨 열(1·2차 클래스, 하위 분류, `p_*`, 신뢰도, 상태, `designation`, `object_id`, `separation_arcmin`, 고신뢰, 부모·구성 역할)이 바뀐 행은 **0개**다. `objects_summary.csv`는 `ra`·`dec`·`position_source`만 다르다. 행 순서와 행 수도 같다. 기본 실행의 출력은 변경 전 코드와 바이트 단위로 같다(NGC 4522 12′, 89개 객체; `Preprocess/tests/test_object_position.py`가 스위치를 켠 전체 파이프라인을 끈 쪽과 열 단위로 비교한다).

## 3. 이동 (`shift.csv`, 전체 253,818개 객체 = 주 표와 갈래·부품 포함)

0″인 객체 **91.47 %**, 0.1″ 넘게 이동 5.34 %, 0.5″ 넘게 2.67 %, 99백분위 1.36″, 최대 20.1″(4XMM 행이 NVSS류 넓은 빔 앵커를 대신한 객체). 인쇄되는 목록: LS 224,570, PS1 20,874(구성원이 PS1뿐이거나 LS 없이), SDSS 2,319, Gaia 3,164, AllWISE 866(이동 0). 보정 9 / 확인 17의 이동 분포는 같다(0.5″ 넘게 2.85 / 2.57 %).
**저위도**(`shift_lowlat.csv`, `lowlat_qso`의 확인 원뿔 140개, |b| 5–20°, 1단계만; 객체 130,577개): 0″ **96.58 %**, 0.1″ 넘게 1.27 %, 0.5″ 넘게 0.42 %, 99백분위 0.144″, 최대 13.76″(NVSS 앵커를 VLASS 행이 대신함). Gaia 고유운동 > 100 mas/yr 별은 깊은 COSMOS에 6개뿐이라(고위도) 고유운동 큰 별의 이동은 이 자료로 시험하지 못했다.

## 4. 정답 쪽 채점 (`rescore_split_*.csv`; 라벨은 같으므로 위치가 일으킨 변화만)

COSMOS2020 STAR/GALAXY(F814W < 24.5) 정답 천체 61,973개. 두 분할(보정 9 / 확인 17, 보정 15 / 시험 11)의 전체 줄:

| 읽기 | 맞음(앵커) | 맞음(best) | 깨짐 | 고침 | McNemar p |
|---|---:|---:|---:|---:|---:|
| `pick`(1.5″ 안에서 목록이 가장 많은 객체 하나의 클래스) | 58,978 | 59,639 | 18 | 679 | < 1e-100 |
| `exists`(0.5″ 안에 정답 클래스의 객체가 있다) | 56,048 | 58,728 | 41 | 2,721 | < 1e-100 |
| `every`(0.5″ 안에 객체가 있고 모두 정답 클래스) | 55,992 | 58,678 | 42 | 2,728 | < 1e-100 |
| **`exists_both_near`**(두 실행 모두 0.5″ 안에 객체가 있는 정답 천체만: 클래스만 본다) | 56,008 | 56,010 | **1** | **3** | 0.625 |

- **라벨의 변화는 0이다**(`exists_both_near`: 고침 3 / 깨짐 1은 같은 정답 원천 근처 객체의 구성이 바뀐 것). `pick`·`exists`의 이득은 모두 **위치가 좋아져 객체가 가까이 온 것**이다: 정답 천체 중 1.5″ 안에 객체가 없는 것 908 → 246개, 0.5″ 안에 없는 것 3,916 → 1,217개. `pick`이 바뀐 707개 중 669개는 앵커 쪽에 짝이 없던 것이고 두 쪽 모두 짝이 있으나 클래스가 다른 것은 31개(맞음 11 → 20)다.
- 따라서 **`pick`·`exists`는 이 변경의 효과를 "라벨 개선"으로 부풀린다**: 앞의 `pick` 보고서들(`METRICS.md` 3절)과 같은 함정이다. 위치를 바꾸는 변형은 `exists_both_near`와 위치 잔차로 말한다.

## 5. 시간 (`timing.csv`)

`object_position.apply`는 영역당 평균 0.028 s(최대 0.041 s; 검출 약 12,200행), 26개 영역 합 0.73 s다. 켠 쪽의 파이프라인은 합 2,360 s, 끈 쪽 2,431 s(같은 영역에서 7 % 차이는 병렬 실행 부하)이므로 `apply`는 전체의 **0.031 %**이다.
