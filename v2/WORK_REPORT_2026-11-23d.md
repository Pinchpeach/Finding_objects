# 작업 보고서 2026-11-23d: 수집 요청 수 줄이기 (2.60.0)

2.59.0(PR #75) 병합 뒤, 계획 세션의 작업 지시서 "2.59 후속, 수집 요청 수 줄이기"를 처리했다. 정상인 날의 실행 시간을 정하는 것은 서버 응답이 아니라 **요청 수 × 요청 전 3–5초 대기**(프로젝트 규칙 2.33.0)라는 전제가 맞는지, 어디서 요청이 나가는지 요청 단위로 분해하고, SIMBAD를 먼저 줄였다. 1차·세부 라벨은 바뀌지 않는다. 대기 규칙도 바꾸지 않았다.

## 2. SIMBAD

### 2.1 요청 단위 분해 (2026-11-23, 요청 URL과 본문을 아래에서 기록)

| 번호 | 요청 | 왜 나가나 | 서버 시간 |
|---|---|---|---|
| 1–2 | `GET simbad.cds.unistra.fr/simbad/sim-tap/capabilities`, 이어서 `.../simbad/capabilities` | astroquery가 TAP 서비스를 만들 때 `capabilities`를 읽는다. 404이면 pyvo가 기본 주소를 한 번 더 시도한다. Strasbourg는 CDS 사고(2026-11-18 공지)로 2026-11-15부터 404다 | 1.0 + 0.1초 |
| 3 | `GET simbad.harvard.edu/.../capabilities` | `hardlimit`(질의 최대 행 수) 확인 | 0.4초 |
| 4–6 | `POST .../sync`: 표 목록(`TAP_SCHEMA`), `basic`의 열, 필터 목록 | `add_votable_fields`가 요청한 필드 이름(`otype`, `sp`, `plx` ...)이 있는지 확인한다. 열 이름을 검증할 뿐 자료가 아니다 | 0.05초씩 |
| 7 | `POST .../sync`: 원뿔 질의 | 자료 | 0.1초 |
| 8 | `POST .../sync`: `otypedef` | 천체 유형 이름표. 0행이어도 물음 | 0.1초 |
| 9… | `POST .../sync`: `has_ref JOIN ref`, `main_id IN (…300개)` | 참고문헌. 천체 300개마다 1번 | 0.15초 |

COSMOS 2′는 3,226천체라 참고문헌 질의가 11번 = 8 + 11 = 19번. 서버가 실제로 일한 시간의 합은 2초 미만이고(요청마다 0.05–1.0초) 나머지는 요청 앞의 3–5초 대기다.

### 2.2 설계와 이유

- **직접 TAP POST 한 번으로 원뿔을 받는다.** 메타 질의 4번과 `capabilities` 2–3번은 필드 이름 검증과 행 상한 확인뿐이라 자료와 무관하다. astroquery가 만든 질의 본문(열 16개, `CONTAINS(POINT, CIRCLE)` 조건)을 그대로 쓰되 요청만 한 번에 보낸다. 열 목록은 astroquery 0.4.11의 질의 본문에서 가져왔고(시험으로 고정), 열 이름이 바뀌면(`plx` → `plx_value`가 그런 사례) SIMBAD가 400을 내므로 **그때는 2.54.0의 astroquery 경로로 돌아간다**.
- **`otypedef`는 같은 질의에 `LEFT JOIN`한다.** `otypedef`는 226행이고 `otype`이 유일하며 공백이 없음을 확인했다(행이 늘어날 수 없다). 별도 요청(고정 표인데 매 프로세스 한 번)이 사라진다.
- **참고문헌은 천체 목록 대신 원뿔 조건을 하위 질의로 쓴다.** `b.oid IN (SELECT oid FROM basic WHERE CONTAINS(...))`. 같은 원뿔의 같은 조건이라 이름 목록(`IN ('M 1', ...)`)과 같은 천체를 가리킨다. 서버 시간(COSMOS 2′, 10,136행)을 재어서 골랐다.

  | 형태 | 서버 시간 | 본문 크기 |
  |---|---|---|
  | 원뿔 조건을 JOIN에 직접 | 8.5초 | 266 B |
  | **하위 질의** | **1.7초** | 313 B |
  | `oid` 목록 3,226개 | 1.5초 | 28.7 KB(`oid`를 먼저 받아야 함) |
  | `main_id` 목록 3,226개 | 3.6초 | 85 KB |

  처음에는 JOIN에 직접 쓴 형태로 구현했다가(NGC 4522에서 참고문헌 질의만 서버에서 7초) 위 표를 재고 바꿨다.
- **한 요청으로 합치지 않았다(원뿔 + 참고문헌).** 참고문헌 열을 원뿔 질의에 붙이면 천체 × 논문 행이 곱해져(COSMOS 2′: 3,226 → 10,136행) 천체 열이 반복되고 큰 원뿔에서 응답이 커진다. 참고문헌은 "실패해도 수집기를 실패시키지 않는" 선택 정보라(`simbad_reference_query_status`), 분리해야 원뿔 자료를 지킨다.
- **행 수 제한.** `MAXREC` = 2,000,000(SIMBAD `capabilities`의 hard limit, astroquery도 같은 값). 응답에 `QUERY_STATUS OVERFLOW`가 있으면 **오류를 낸다(잘린 목록을 정상으로 보이지 않게)**. 측정: COSMOS 반경 10′ 59,540천체, 요청 3번(Strasbourg 404 포함), 58.6초, 최대 메모리 788 MB. 20′ 192,486천체, 요청 2번, 161.6초, 1.9 GB. 시간은 요청이 아니라 VOTable 해석이 정한다. 기존 경로는 같은 10′에 참고문헌만 약 200번(약 13분: 계산, 측정하지 않음)이라 사실상 쓸 수 없었다.
- **동률 정리 (결과가 달라지는 곳).** 참고문헌 3편은 `obj_freq` 내림차순, 연도 내림차순으로 고르는데 두 값이 같은 논문은 서버가 답한 순서가 정했다. 이 순서는 질의 형태에 따라 달라진다. COSMOS 2′에서 3,226천체 중 3,215개가 참고문헌이 있고, 그중 **37개(1.2 %)의 3편이 동률이라 기존과 다르다**. `bibcode` 오름차순을 마지막 기준으로 넣어 서버 순서와 무관하게 정했다. 독립 계산한 상위 3편과 3,215/3,215가 일치한다. 이 값은 앱의 문헌 표시(`paper_refs`, `paper_ads`)에만 쓰이고 분류에는 쓰이지 않는다(`Classifier/literature.py`). 세 영역 전체 파이프라인에서 달라진 것은 COSMOS의 37개 천체의 `paper_refs`·`paper_ads` 둘뿐이다.
- **열 순서.** astroquery 경로의 출력 열 순서는 프로세스마다 달랐다(같은 코드의 두 실행에서 `rvz_redshift, pmdec, pmra` / `pmra, pmdec, rvz_redshift`). 이제 고정이다. 하류는 열 이름으로 읽는다.

### 2.3 실패한 서버를 뒤로 미루는 기억

- `throttle.py`의 VizieR 미러 순서 기억과 같은 방식이다. `archive_cache.note_source(key, ok)` / `source_down(key)`: 실패는 `V2_FAILURE_MEMORY_S`(기본 600초, 0이면 끔)동안 `<캐시 폴더>/sources.json`에 두어 **프로세스 사이에서** 공유한다. 어떤 응답이든 받으면 실패를 지운다. `V2_CACHE=0`이면 기억도 끈다.
- **순서만 바꾼다. 서버를 건너뛰지 않는다.** Harvard가 실패하면 Strasbourg를 다시 묻는다(시험으로 고정).
- 효과: Strasbourg 404가 매 검색 요청 1번(이전 2번)과 대기 3–5초를 쓰던 것이 연속 검색에서는 0번.
- 대안으로 본 것: IDIA 미러(`simbad.idia.ac.za`)를 세 번째 서버로 추가. `capabilities`는 200이지만(1.5초) 같은 자료인지 확인하지 않아 넣지 않았다.

## 3. 요청 로그 고치기

- `[http]` 로그는 `requests`를 거치는 요청만 찍었다. Gaia의 astroquery TAP 클라이언트는 `http.client`를 직접 쓰므로 Gaia 요청이 로그에 없었다. `throttle._logged_client`가 이 경로를 한 줄씩 찍는다(`requests`를 거친 요청은 중복으로 찍지 않는다: `_local.via_requests`).
- 수집기가 시작한 보조 스레드는 이름이 `Thread-N`이었다(`desi_legacy`의 TAP / 뷰어 스레드, `gaia_dr3`의 TAP 스레드, `atnf_pulsar`의 HEASARC 스레드). `throttle.child_name("tap")`으로 `<수집기>/<작업>` 이름을 붙였다(`gaia_dr3/tap`). `request_counts.py`는 `/` 앞의 이름으로 수집기에 합산한다.
- 이 기록을 표로 만드는 `v2/benchmark/request_counts.py`를 넣었다(수집기별 요청 수·호스트·경과 시간, 대기를 달리할 때의 계산: 5절).

## 4. 수집기별 요청 수 (차가운 새 영역)

### 4.1 측정 환경이 계획 세션의 17–31번과 다른 이유

처음 "전"을 잰 두 번은 VizieR 수집기가 요청 0번, 0.01–0.08초로 끝났다. **astroquery가 VizieR 응답을 디스크(`~/.cache/astropy/astroquery/Vizier`)에 저장하고, `Vizier.query_region(cache=True)`가 명시 기본값이라 컨트롤러의 `cache_conf.cache_active = False`(2.19.0)와 `V2_CACHE=0`이 효과가 없다.** 같은 영역을 다시 돌리면 7일 동안 요청 없이 끝난다. 계획 세션의 17–31번(SIMBAD가 절반)은 이 따뜻한 조건의 값으로 보인다. 새 영역은 VizieR 요청이 57–60번 더 나간다. 아래 "차가운" 측정은 `XDG_CACHE_HOME`을 비어 있는 폴더로 두고(폴더가 먼저 있어야 astropy가 인정한다) 잰 것이다.

**이 캐시는 고치지 않았다.** 결과가 같고 응답 보존 기간이 7일이라 위험은 작지만 (1) `V2_CACHE=0` 측정이 오염되고 (2) 크기 제한이 없다(2.19.0 주석: "never pruned"). `vizier_query`에서 `cache=False`를 넘기면 끌 수 있고, 이는 사용자가 정할 일로 둔다.

### 4.3 VizieR가 한 카탈로그에 6–13번 묻는 이유

`agb_suh2021`(카탈로그 4개)의 COSMOS "전" 요청 13번:
`vizier.cfa.harvard.edu`가 표 없이 200(1), 확인 요청에서 "no table" 응답(2)(= CfA 미러에 그 카탈로그가 없다) → `vizier.nao.ac.jp` 연결 거부 → `vizier.iucaa.in` 읽기 시간 초과 10초 → `vizier.china-vo.org` 연결 거부 → `vizier.idia.ac.za`가 표 없이 200 + 확인 "empty table"(= 카탈로그가 있고 원뿔이 비었다)(2). 카탈로그 4개가 각각 이 순회를 한다.
- 순회에서 죽은 미러 3곳(NAO, China-VO, IUCAA)으로 간 요청이 영역마다 6–7번(NGC 7, COSMOS 6, 은하면 6)이고 대기 33–43초 + 3–5초 대기 24–28초, 합 약 57–71초의 스레드 시간이다.
- 빈 원뿔마다 확인 요청이 1번 더 있다(20–25번): 2.47.0, 2.54.0의 규칙(미러가 카탈로그 없이 표 없이 답하는 것과 빈 원뿔을 구분). **이 규칙은 건드리지 않았다**: 2026-11-07의 사고(CfA가 모든 카탈로그에 표 없이 답해 520개 검증 천체가 빈 결과)에서 나온 것이라 "이 미러는 믿어도 된다"는 기억을 디스크에 두면 같은 사고가 기억 기간 동안 조용히 되살아난다.

### 4.4 같은 방식으로 줄인 것: 죽은 미러를 프로세스 사이에서 기억

`throttle.py`가 이미 가진 미러 순서 기억(`_unreachable`, 프로세스 안, 연결 거부만)에 더해, 거부·시간 초과·`RETRY_STATUS`로 실패한 VizieR 미러를 `note_source`로 디스크에도 둔다. 다음 검색은 그 미러를 맨 뒤로 보낸다(응답하면 지움). 순서만 바꾼다.

| 검색 | 죽은 미러로 간 요청 | 전체 요청 |
|---|---|---|
| "전", 영역 세 곳 각각 | 7 / 6 / 6 | 91 / 96 / 83 |
| "후", 기억 없음(캐시 끔) | 15 / 6 / 12 | 96 / 83 / 89 |
| "후", 연속 검색 첫 번째(COSMOS) | 12 | 95 |
| "후", 연속 검색 두 번째(NGC 4522) | **0** | 80 |
| "후", 연속 검색 세 번째(은하면) | **0** | 73 |

기억이 없을 때는 오히려 한 실행에서 15번까지 갔다(미러 상태가 시각마다 다르다). 연속 검색에서는 두 번째·세 번째가 0번이다. 첫 검색은 줄지 않는다(기억할 것이 아직 없다).

### 4.5 Gaia (26–30초)의 요청 구성

`gaia_dr3`는 요청 5번 + 시작 시 1번이다.

| 번호 | 요청 | 무엇 |
|---|---|---|
| 0 | `GET gea.esac.esa.int/tap-server/tap/notification` (메인 스레드) | `import astroquery.gaia`가 서버 알림을 읽는다(`GaiaClass(show_server_messages=True)`). 컨트롤러가 먼저 읽는(`_preload`) 때문에 **모든 수집기가 시작하기 전에 3–5초를 직렬로 쓴다**. 점검 공지(11-25 12:00 CET)도 여기서 나온다 |
| 1 | `POST .../tap/sync` | 기준 원뿔 질의(`gaia_source`) |
| 2 | `POST .../tap/sync` | `astrophysical_parameters`(AP + SPEC_AP) |
| 3 | `POST .../tap/sync` | `vari_classifier_result` |
| 4 | `POST .../tap/sync` | `vari_summary` |
| 5 | `POST dc.zah.uni-heidelberg.de/tap` | 천문측량 충실도(GAVO) |

2.56.0의 동기 우선 이후 비동기 요청(제출, 상태 확인, 결과)은 없다. 5번 × 대기 4초 + 서버 응답이 약 28–30초다.

**줄일 수 있는 것(구현하지 않음):** (1) 요청 2–4를 하나의 `LEFT JOIN`으로 합치면 −2번(약 −8초). 표마다 `gaia_*_query_status`를 따로 두는 실패 격리(한 표가 실패해도 다른 표와 기준 천체는 유지)가 사라지므로 합친 질의가 실패하면 지금의 순차 경로로 되돌아가는 구조가 필요하다. (2) GAVO를 ESA 요청과 동시에 보내면 대기가 겹친다(요청 수는 그대로, 약 −4초). (3) 시작 알림 요청은 점검 공지를 주는 기능이라 없애지 않았다. 차가운 영역에서 임계 경로는 Gaia가 아니라 VizieR이라 지금은 수집 전체 시간이 줄지 않는다(정상인 날의 임계 경로는 Legacy Surveys 약 35초와 Gaia 약 26–28초라 이때는 효과가 있다).

### 4.6 다른 수집기

- `sdss_dr18`, `sdss_spectroscopy`(4–11번): SkyServer가 `403 - Forbidden` 오류 페이지를 주고 2.56.0의 규칙이 1초 뒤 다시 묻는다. 정상인 날은 1–2번(계획 세션 로그). 이 컨테이너에서 계속 보였다.
- `galaxy_clusters`(3–4번): 카탈로그 3–4개. `ztf_periodic`, `bzcat`, `twomass`, `lamost_spectroscopy`: 위 미러 순회가 원인(해당 카탈로그를 CfA 미러가 가지지 않는 날).
- `desi_fastspec`: Data Lab이 정체될 때 2번(2.59.0의 2 × 50초). 이 날 NGC 4522·COSMOS의 12번 중 6번이 102초 시간 초과, 1번이 76초 오류, 1번이 68초 성공이었다(정상은 4.9–19초). 아래 5절이 이 정체의 영향을 따로 계산하는 이유다.

## 5. 정상인 날(VizieR 응답 있음)의 효과

계획 세션과 같은 조건(VizieR 디스크 캐시 있음, 캐시 끔)에서 "후"를 한 번 더 쟀다. Data Lab이 이 날 정체해 NGC 4522(102초 시간 초과)·COSMOS(오류 77초)의 수집 시간은 FastSpecFit이 정했다. 그래서 정상인 Data Lab(탐침 중앙값 11초)을 두고 컨트롤러와 같은 6 스레드 목록 스케줄링으로 다시 계산한 값을 같이 둔다(모형은 측정보다 낮다: 차가운 영역 3.5–4.9 %, 따뜻한 영역 6–16 %. 수집 시작 전의 시작 요청과 모듈 읽기를 세지 않는다. 위 값의 차이는 이 오차보다 크다).

| 영역 | 전: 측정 / 모형 / FastSpecFit 11초 | 후: 측정 / 모형 / FastSpecFit 11초 | 요청 수 전 → 후 |
|---|---|---|---|
| NGC 4522 2′ | 111.4 / 102.4 / 41.6 (50.7: 두 번째) | 110.7 / 102.3 / **36.1** | 24 → 20 (SIMBAD 9 → 3) |
| COSMOS 2′ | 110.4 / 103.5 / 92.5 (87.7) | 86.1 / 77.4 / **35.2** | 44 → 26 (SIMBAD 19 → 3) |
| 은하면 1′ | **44.6** / 39.2 / 39.2 | **30.9** / 26.0 / 26.0 | 29 → 18 (SIMBAD 8 → 2) |

은하면 한 곳만 Data Lab이 필요 없어 측정이 직접 비교된다(−13.7초, −31 %). COSMOS는 SIMBAD가 임계 경로였으므로(81초) 효과가 가장 크다(모형 92 → 35초). 이 둘은 계산이라 정상 날 재측정으로 확인해야 한다.

## 7. 서비스 이용 한도와 대기 (조사만, 대기 규칙은 그대로)

`v2/Get_data/LITERATURE_ARCHIVE_LIMITS_2026-11-23.md`: 서비스별 원문 인용, 출처 URL, 확인 방법. 요약:
- 공식 속도 한도를 읽은 것은 **NED**("Do not query NED more frequently than 1 per second", "Do not run multiple concurrent automated queries; single-thread interactions only")와 **SDSS SkyServer**(DR16 문서: 분당 60회)뿐이다. 두 인용은 내가 원문을 직접 다시 읽어 확인했다(Gaia 할당량 표와 CDS 공지도).
- **CDS는 2026-11-18부터 사이버 보안 사고로 SIMBAD·VizieR 공식 문서가 모두 404**라 SIMBAD·VizieR의 공식 속도 한도를 읽지 못했다. SIMBAD의 2차 자료(astroquery 문서: ~5–10회/초 또는 6회/초 초과 시 차단)는 서로 다르다. Strasbourg 404의 원인이 이 사고로 보인다.
- 나머지(Data Lab, MAST, IRSA, HEASARC, GAVO, Gaia, Legacy Surveys)는 요청 속도·동시성 한도를 찾지 못했다(행·시간 제한만 있음).
- 대기를 달리하면(`request_counts.py --whatif`, 계산): 공식 한도가 있는 서비스만 1초 → 차가운 영역에서 −2…−7초, 정상인 날 0초. 모든 호스트 1초(근거 없는 상한) → −38…−43 %(차가운), 정상인 날 −6…−15초. **지금 문서가 근거를 주는 범위의 대기 단축은 거의 효과가 없고, 요청 수를 줄이는 것이 낫다.** 대기 규칙은 사용자가 정할 일이라 바꾸지 않았다.
- 대기가 스레드 시간의 52–70 %다(수집기 경과 시간 합 대비 요청 수 × 4.0초).

## 9. 한계와 남은 것

- **수집 전체 시간은 차가운 영역에서 거의 줄지 않았다.** 임계 경로가 SIMBAD가 아니라 VizieR 미러 순회와(`agb_suh2021` 84–110초가 9번의 차가운 측정 중 7번 최장) Data Lab 정체다. 이 둘이 이번 측정의 ±40초 흔들림이다. SIMBAD의 요청 수·시간 감소는 확실하고 정상인 날의 임계 경로에서는 효과가 크지만, 차가운 새 영역의 체감은 VizieR 미러 상태가 정한다.
- 다음에 효과가 큰 것(구현하지 않음):
  1. **카탈로그 단위 미러 순서 기억**("CfA는 이 카탈로그가 없다"를 하루 기억해 그 카탈로그는 처음부터 IDIA를 먼저 묻기): `agb_suh2021`만 해도 카탈로그 4개 × 요청 2번 = −8번(약 30초). 순서만 바꾸므로 안전하지만 별도 TTL이 필요하다.
  2. 빈 원뿔의 확인 요청(20–25번)은 2.47.0 사고 때문에 그대로 두었다.
  3. Gaia 선택 표 3개를 하나로(−2번), GAVO 병행.
  4. 시작 알림 요청(약 4초 직렬)을 수집과 겹치기.
- 측정 범위: "전"은 영역마다 한 번(SIMBAD 단독은 3–4번), "후"는 영역마다 한두 번이다. VizieR 미러 상태가 시각마다 달라 합계 요청 수의 차이(예: 91 → 96, 83 → 89)는 SIMBAD 감소보다 큰 잡음이다. 이 날 Gaia는 ESA 원본이었다(점검은 11-25 12:00 CET부터).
- 정상인 날의 수집 시간(5절의 모형값)은 Data Lab이 정상인 날에 재서 확인해야 한다.
- 범위 밖으로 둔 것: 대기 규칙 변경, 분류 코드 변경, 깊은 COSMOS 수집, DR4 전환.
