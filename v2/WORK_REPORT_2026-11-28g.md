# 작업 보고서 2026-11-28g — 과제 버: 출력 위치를 연결 순서에서 분리 (`V2_OBJECT_POSITION=anchor|best`)

버전 제안 **2.62.12 (PATCH)**: 스위치는 기본 꺼짐이고 꺼진 출력은 이전 코드와 바이트 단위로 같다(NGC 4522 12′ 확인). 켜면 사용자에게 보이는 `ra`·`dec`가 바뀌므로 **기본값으로 올리는 것은 MINOR**다(계획 세션의 지시 그대로).

## 0. 내가 이해한 요청

계획 세션(04:00 UTC 수신, 05:53에 읽음)의 과제 버를 이렇게 이해했다. (1) 다중 목록 객체의 대표 좌표를 정하는 관례를 원문으로 확인하고(가장 정밀한 측정 대 역분산 가중 평균, Gaia·ICRS·에포크·고유운동, SIMBAD·NED의 기본 좌표 규칙); (2) 구현: 출력 좌표 열만 바꾸고 **연관·분류에 쓰이는 값은 그대로**임을 하류 사용처 전수 확인(조각 규칙, 숙주 은하·그룹, 저위도 |b|, 소광, 풋프린트, 앱 지도·내보내기, `object_id`)으로 보이고, 출력 좌표만 바꿨는데 라벨이 바뀌면 설계가 틀린 것으로 본다; (3) 우선순위 규칙은 목록의 문서 정확도와 측정 오차(하한 적용)로 정하고 어느 목록의 좌표인지 `position_source` 열에 적고, 고유운동이 큰 별의 에포크 문제를 다룬다; (4) 측정: 깊은 COSMOS 보정 9 / 확인 17로 나누고 **예측을 먼저**, 정답 대비 위치 잔차(중앙값, 90·99 백분위, 0.3/0.5/0.7/1.0″ 밖, 앵커 목록별·등급별), 라벨 변화(0이어야 함), 조각 수, `pick`·`exists` 채점에 주는 영향, 저위도·실사용 영역의 좌표 이동 분포, 속도; (5) 기본값은 바꾸지 않는다.
**순서에 대한 고백**: 지시는 러 → 버 → 머 → 서였는데 메시지를 늦게 읽어 머를 먼저 했다(앞 보고서 28f 참고). 서(분할 고정)는 이 보고 뒤에 한다.

## 1. 요약

* **결과**: 깨끗한 객체 136,816개에서 정답(COSMOS2020)과의 거리가 0.5″를 넘는 비율이 앵커 **4.51 % → 1.35 %**(보정 9 4.75 → 1.39, 확인 17 4.37 → 1.33), 1.0″ 밖 1.94 → 0.23 %, 99백분위 1.485″ → 0.531″. AllWISE가 앵커인 객체는 **71.4 % → 1.0 %**(중앙값 0.78″ → 0.052″), Pan-STARRS1이 앵커인 객체는 17.4 → 3.4 %.
* **설계의 핵심 조건 충족**: 26개 영역 전체 파이프라인을 스위치 끔·켬으로 돌려 `classified_objects.csv`를 열 단위로 비교하면 **`ra`·`dec`만 다르고 라벨·확률·이름·거리·객체 집합이 바뀐 행은 0개**다(`objects_summary.csv`는 `ra`·`dec`·`position_source`만).
* **정답 쪽 채점은 위치의 효과일 뿐 라벨의 효과가 아니다**: `pick` +661(+1.07 %p), `exists` +2,680(맞음 56,048 → 58,728 / 61,973)은 정답 천체 근처에 객체가 오게 된 것(0.5″ 안에 객체가 없는 정답 천체 3,916 → 1,217개)이고, **클래스만 보는 `exists_both_near`는 +2(고침 3, 깨짐 1)**다.
* 이동: 객체의 91.5 %는 0″, 0.5″ 넘게 이동 2.7 %, 99백분위 1.36″, 최대 20.1″(NVSS·4XMM류 넓은 오차 앵커). 저위도 원뿔 140개(객체 130,577개): 0″ 96.6 %, 0.5″ 넘게 0.42 %, 99백분위 0.14″. 속도: `apply` 영역당 0.028 s(전체의 0.031 %).
* **틀린 것 둘**: 첫 구현의 동점 규칙(3.24 %, 28d의 3.16 %를 재현하지 못함)과 Pan-STARRS1의 오차(문서의 `raMeanErr`를 위치 오차로 읽으면 PS1이 LS를 이긴다). 둘 다 고쳤고 이력을 §6에 적었다. **PS1 바닥 0.6″는 같은 자료를 본 뒤에 고른 값이다(검증이 아님)**.

## 2. 문헌 (`LITERATURE_OBJECT_POSITION_2026-11-28.md`)

원문 확인: Wenger et al. 2000(SIMBAD)은 "most accurate" 측정 하나를 기본 좌표로 고르고 나머지는 측정값으로 남긴다(품질 A–E, 오차 타원, ICRS 에포크 2000.0 표시). Wilson & Naylor 2018(arXiv:1710.04896, 7절)은 여러 목록을 가장 정밀한 것부터 차례로 맞추며 **가중 평균 위치**를 쓰되 오차 분포는 더 정밀한 쪽의 것을 그대로 쓰길 권한다. Makarov et al. 2023(RORC, VI절)은 **목록 사이 계통 차(벡터 구면조화)를 먼저 빼고** 공분산 가중 평균을 낸다. **읽지 못한 것**: NED의 대표 위치 선택 규칙(도움말 403/404; 열린 FAQ는 적색편이만), SIMBAD의 현재 사용자 안내서(404; 2000년 논문만 확인). 이 둘은 근거로 쓰지 않았다.
결론: **가중 평균이 아니라 가장 정밀한 구성원 하나**. 이유 (가) SIMBAD가 같은 규칙, (나) 가중 평균의 이득은 계통 차를 뺀 뒤에 있는데 우리는 그 보정이 없다, (다) 에포크가 다른 좌표를 섞으면 고유운동이 큰 별의 좌표가 어느 시점의 것도 아니다, (라) 우리 자료: 28d의 설계 비교에서 `ivw_mean`(3.28 %)이 `best_member`(3.16 %)보다 낫지 않았다.

## 3. 설계와 이유

| 선택 | 대안과 버린 이유 |
|---|---|
| **최종 표를 쓰기 직전에 한 번 바꾼다**(`object_position.apply`, `pipeline.py`의 마지막) | (a) 1단계에서 앵커 선택 규칙을 바꾸기: 러에서 `floored`가 AllWISE `right_object` −179, `displaced` +173으로 **연관이 나빠졌다**; 연관을 건드리지 않는 것이 과제의 조건이다. (b) 2단계의 객체 `ra`/`dec`를 바꾸기: 하류에 좌표를 쓰는 곳이 열 군데가 넘는다(`DOWNSTREAM_USE.md`); 펄서 사후확률은 `|b| < PSR_PLANE_B`의 **문턱**이라 좌표를 1″ 옮기면 라벨이 뒤집힐 수 있다. 마지막에 바꾸면 이런 곳이 모두 앵커 좌표로 끝난 뒤다. |
| 새 열은 스위치를 켤 때만, 맨 끝에 | 끈 출력이 이전 코드와 바이트 동일해야 하고(다른 스위치와 같은 규칙) 앱은 새 열을 몰라도 된다. |
| 한 구성원의 좌표를 그대로(평균 없음), 시점은 `position_epoch`에 기록 | 가중 평균은 위 §2. 공통 시점으로 옮기는 고유운동 보정은 하지 않았다: 앵커도 같은 한계를 갖고, 보정에 쓸 고유운동은 Gaia 행이 있을 때만 있는데 그때는 Gaia가 이미 뽑힌다. |
| 순위 오차 = 연관의 유효 오차 + **PS1 바닥 0.6″** | 연관과 같은 정의를 쓰면 `position_residual.py`의 28d 설계 비교와 직접 이어진다. PS1은 문서의 `raMeanErr`(단일 에포크의 흩어짐; `UNITS.md`)를 오차로 읽는 것이 틀려서 바닥을 따로 두었다. 바닥은 **출력 위치를 고르는 순위에만** 쓰고 연관은 그대로다. |
| 동점: 바닥 밑의 측정 오차 → 목록 우선순위 → 이름 → 검출 id | 바닥이 같은 광학 목록끼리(LS·PS1·SDSS 모두 PSF/6 = 0.2″) 동점이 흔하다(깨끗한 객체 2,034개). 우선순위만으로 가르면 3.24 %, 측정 오차를 먼저 보면 3.16 %. 입력 순서에 의존하지 않는다(섞기 시험). |
| `ra_anchor`/`dec_anchor`를 남김 | 되돌릴 수 있고, 하류가 쓴 좌표를 추적할 수 있다. |
| `designation`·`separation_arcmin`·원뿔 자르기는 앵커 좌표 그대로 | 이름은 목록 식별자에서 오고 좌표에서 오지 않는다. `separation_arcmin`은 표시 좌표와 `position_shift_arcsec`만큼(99백분위 1.4″ = 0.023′) 어긋날 수 있다: 문서화한 한계. |

## 4. 하류 좌표 사용처 전수 (`benchmark/object_position/DOWNSTREAM_USE.md`)

`grep`으로 객체 `ra`/`dec`를 읽는 곳을 표의 14항목으로 모두 적었다: 연관은 검출 행의 좌표를 쓰고 객체 좌표를 읽지 않는다(`object_id`는 순번 `OBJ%06d`). 2단계 큰 은하 숙주 표지, 5단계 은위도·마젤란 구름 사전확률, 저위도 QSO·어두운 별:은하·희박 사전확률·근적외 별 규칙, 하위 분류의 시선 방향 먼지 분율과 펄서 `|b|` 문턱, 숙주 묶음·PS1·LS 조각·후광 인공물(`host_groups.py`), PS1 단독 인공물, 전파 단독, 은하단 구성원은 모두 7단계 또는 그 뒤의 후처리 안에서 앵커 좌표로 끝난다. 소광은 목록의 `std_ebv` 열을 읽을 뿐 좌표로 지도를 찾는 곳이 없다. **바뀌는 곳은 의도한 둘**: 요약 표(`ra`, `dec`, 새 열 `position_source`)와 앱의 표·하늘 지도·책갈피(표의 `ra`/`dec`를 읽음).

## 5. 측정 (`benchmark/object_position/results_2026-11-28/README.md`에 전부)

핵심 표는 위 §1과 README. 여기에 더하는 판단 둘.

* **`pick`·`exists`의 증가를 "라벨이 좋아졌다"로 읽으면 틀린다**: 이득은 전부 정답 천체 가까이에 객체가 오게 된 것이다(1.5″ 안에 객체가 없는 정답 천체 908 → 246, `pick`이 바뀐 707개 중 669개는 앵커 쪽에 짝이 없던 것, 짝이 둘 다 있고 클래스가 다른 것 31개: 11 → 20 맞음). 위치를 바꾸는 변형의 라벨 효과는 `exists_both_near`와 위치 잔차로 말한다(`METRICS.md` 3절의 규칙과 같다).
* **PS1 앵커 객체는 3.4 %가 남는다**: 이 객체들 중 `best`가 PS1을 뽑는 경우(LS 행이 없는 933개 중 22.7 %가 0.5″ 밖)가 남는다. 더 좋게 하려면 PS1의 위치 오차를 등급의 함수로 모델링해야 하는데(i > 24에서 PS1 위치의 85 %가 0.5″ 밖) 이번에는 하지 않았다.

## 6. 오류와 고친 것

* **첫 구현의 동점 규칙**이 목록 우선순위만 써서 3.24 %(예측 3.16 ± 0.02 %)였다. 28d의 `best_member`는 입력 순서로 가렸고 그 순서가 우연히 측정 오차 순이었다. 측정 오차를 동점의 첫 열쇠로 넣어 3.156 %로 재현했다. (예측 P1 틀림.)
* **PS1 앵커 17.35 %**(예측 ≤ 5 % 틀림): 위 §3. PS1 바닥 0.6″를 넣었다. **이 값은 같은 자료를 보고 정했고 한 값만 시도했다**(훑지 않음). 보정 9(1.39 %)와 확인 17(1.33 %)이 같은 방향이지만 같은 COSMOS 영역이라 독립 검증은 아니다. 다른 하늘(예: 저위도)에서 PS1·LS의 상대 정확도가 다를 수 있다.
* 첫 전체 실행이 디스크를 채웠다: 영역 하나의 단계별 표가 0.6 GB라 26개 × 2회가 30 GB를 넘었다. 실행을 영역마다 "끔·켬 → 측정 → 작업 폴더 삭제"로 바꿨다(`run_pipeline_both.sh`). 오래된 임시 결과(이미 커밋된 과제의 중간 산출물)를 지웠다.
* 예측 문서에 독일어 문단을 잘못 썼다가 한국어로 고쳤다(내용은 같음).
* 시험 `test_pan_starrs1_...`가 처음에는 실패했다: 바닥을 순위 오차에는 넣고 동점의 측정 오차에는 안 넣어서 PS1이 동점에서 이겼다 → 측정 오차에도 같은 바닥을 적용.

## 7. 한계

* 고유운동이 큰 별에서 `best`가 시점이 다른 목록의 행일 수 있다(앵커도 같음). 깊은 COSMOS에는 그런 별이 6개뿐이라 **시험하지 못했다**.
* 실사용 3개 영역 중 COSMOS 2′와 은하면의 원자료가 이 환경에 없어 NGC 4522 12′(89개 객체)만 스위치 끔·켬 전체 파이프라인을 돌렸다. 은하면은 저위도 원뿔 140개의 1단계 이동 분포로 대신했다(전체 파이프라인 아님).
* NED·SIMBAD의 대표 위치 규칙을 원문으로 못 읽었다. SIMBAD·NED 행은 후보에서 빼지 않으며 기본 오차(0.6″)를 받아 다른 목록보다 정밀한 일이 드물다.
* 표시 좌표와 `separation_arcmin`·원뿔 자르기의 어긋남(99백분위 1.4″).

## 8. 시험

`Preprocess/tests/test_object_position.py` 12개: 스위치 값, 연관의 유효 오차와 일치, 가장 정밀한 구성원·Gaia 우선, 전파 행(legacy 단위 오차)이 이기지 못함, 동점 규칙(우선순위·측정 오차), PS1 바닥, 행 순서 무관, 기본 모드는 표를 그대로 반환, 켜면 `ra`/`dec`와 6개 열만 바뀜, 빈 검색, **스위치를 켠 전체 파이프라인이 기본 실행과 `ra`/`dec` 말고 모든 열이 같음**(NGC 4522 12′). 전체 시험 통과. `benchmark/object_position/`의 도구는 `run_info.json`을 남긴다(실행 입력 해시).

## 9. 결정이 필요한 것 (검토 세션)

1. **기본값으로 올릴지**: `best`를 기본으로 하면 `ra`/`dec`가 모든 사용자 출력에서 바뀐다(MINOR). 이득(0.5″ 밖 4.51 → 1.35 %)과 비용(`separation_arcmin`과의 1.4″ 어긋남, 이름이 아니라 좌표만 바뀜)을 검토 세션이 정한다. 올릴 때 README·개요의 좌표 설명과 앱의 열 설명을 고쳐야 한다.
2. 앱에서 `position_source`를 보여 줄지(지금은 요약 표에 열이 생기고 앱은 몰라도 동작한다).
3. PS1의 위치 오차를 등급의 함수로 모델링할지(§5): 같은 방식으로 3.4 %의 일부를 더 줄일 수 있다.
4. **`floored`(순서 키)를 버릴지**: 이 과제로 위치는 연관을 건드리지 않고 얻게 되었으므로 `floored`의 위치 이득(0.5″ 밖 4.51 → 3.27 %)을 이유로 연관을 바꿀 필요가 없다. 러의 결과(`floored`는 AllWISE `right_object` −179)와 합치면 승격 대상이 아니다.
