# 작업 보고서 2026-11-14: 고정 STAR 모델 검증 입력을 저장소로 (2.53.1), 잠근 세트 C 2.52.0 채점 (2.53.2)

## 1. 요약

`validate-star-diverse.yml`(고정 STAR 백색왜성 판별 모델의 LAMOST 다양 정답 검증)은 고정 모델을 run 36295747956의 아티팩트에서 내려받았다. 그 아티팩트가 2026-10-27에 만료되어 이후 모든 실행이 내려받기 단계에서 실패했다. 2.53.0의 백색왜성 XP 표와 같은 근본 해결로, 고정 모델과 평가 입력을 저장소(`v2/Classifier/star_diverse_validation/inputs/`)에 두었다. 분류 결과는 바뀌지 않는다(PATCH).

| 파일 | 내용 |
|---|---|
| `frozen_star_wd_classifier.joblib` | 고정 모델(run 36295747956), SHA256 `22ae268a…` = 프로토콜 기록값 |
| `frozen_star_gaia_features.csv.gz` | 그 모델의 원래 SDSS Gaia 특징표(내부 test 183/194 재현용) |
| `external_gaia.csv.gz` | 고정 다양 정답(`truth.csv`)의 Gaia 2″ 매칭 |
| `previous_gaia.csv.gz` | 이미 검사한 LAMOST 집합의 Gaia 매칭(source ID 중복 제외용) |
| `SHA256SUMS` | 발표된 실행이 쓴 원본 파일의 해시 |

## 2. 왜 이렇게 짰나

- **어디서 되살렸나.** 원래 모델 아티팩트는 이미 없다. 하지만 그 모델로 발표 결과를 낸 실행 36306280498의 전체 아티팩트(`star-diverse-frozen-validation`, 2026-12-26 만료)에는 그 실행이 내려받은 모델이 그대로 들어 있다. 이 컨테이너는 아티팩트 저장소에 직접 접속할 수 없어서, 워크플로가 한 번만 그 아티팩트를 읽어 저장소에 커밋하게 했다.
- **왜 다시 학습하지 않았나.** 프로토콜(`STAR_DIVERSE_PROTOCOL.md`)이 "저장된 모델 자체를 쓰고, 다시 학습·보정·문턱 선택을 하지 않는다"고 정해 두었다. `validate-star-wd-classifier.yml`로 같은 코드를 다시 돌려 모델을 만들 수는 있다. 그러나 그것은 고정 모델이 아니고 해시도 달라 사전 등록 검증의 의미가 없어진다. 그래서 원본 바이트를 보존하는 길만 택했다.
- **커밋 전 검증.** 되살린 모델은 프로토콜에 적힌 SHA256과 맞아야 한다. 또 저장소의 `metrics.json`(발표 결과)을 그대로 재현해야 한다(해시, 감사 수, 혼동행렬 4개, log loss, Brier, 기준선 적용 비율). 둘 다 통과한 뒤에만 커밋한다. 이후 모든 실행도 같은 재현 확인을 하므로, 이 워크플로는 이제 평가 코드(`evaluate_star_diverse.py`, `train_validate_star_wd.prepare`)의 회귀 시험 역할도 한다.
- **pickle 보안.** joblib 파일은 pickle이라 불러오면 코드가 실행될 수 있다. 그래서 워크플로는 불러오기 전에 매번 SHA256을 확인한다.
- **refresh.** `refresh=true`는 정답과 Gaia 매칭을 새로 모아 고정 모델을 평가하되 아무것도 커밋하지 않는다. WD XP 표의 refresh와 다른 점이다. 프로토콜이 정답을 고정하므로(해시 기록), 새 수집은 수집기 점검용일 뿐 기준 자료를 바꾸면 안 된다.
- **CSV는 gzip(-n)으로.** 원본 해시는 `SHA256SUMS`에 남기고, 저장 크기를 줄이려고 `gzip -n`으로 압축했다(-n은 시간 기록을 빼 같은 입력이면 같은 바이트가 나오게 한다). pandas는 .gz를 그대로 읽으므로 평가 코드는 바꾸지 않았다.

## 4. 잠근 세트 C 2.52.0 채점 (2.53.2)

### 무엇을 했나
2.52.0(commit `16cfdc3`)을 잠근 세트 C(60개 영역, `benchmark/LOCKED_TEST_SET_C.md`)로 한 번 채점했다. run 43390993247의 세 번째 시도에서 점수가 나왔다. 앞의 두 시도는 Legacy Surveys가 느려서 채점 직전 아카이브 관문에서 멈췄다. 그래서 이 판의 한 번뿐인 채점 기회는 쓰이지 않았다.

### 결과

오류 수는 집계 값(재현율, 정밀도, 다수 클래스 기준선)에서 거꾸로 셌다. 예를 들어 2.52.0의 별은 3,170 × 95.24 % = 3,019개이고, 그중 99.83 %인 3,014개를 맞혔다.

### 어떻게 읽나
- **2.51.0과 오차 안에서 같다.** 오류 차이는 12 → 11개이고, 신뢰구간도 거의 겹친다.
- **이 결과는 예상과 맞는다.** 2.52.0은 주로 어두운 별:은하 사전확률을 바꿨다(COSMOS 시험 영역 +1.66점). 세트 C의 정답은 분광이고 약 95 %가 별이며, 은하는 약 144개뿐이다. 그래서 이 숫자가 움직일 이유가 적었다. COSMOS 개선을 확인해 주는 결과는 아니다.
- **두 채점의 자료가 똑같지는 않다.**
  - 2.51.0 채점 때는 `desi_legacy`가 60개 영역 중 5개(8.3 %, 10 % 관문 아래)에서 실패했다. 이번에는 핵심 수집기 실패가 0이었다.
  - 그 결과 정답 천체가 20개 늘었고, 정답이 있는 영역이 하나 늘었으며, Gaia DSC가 있는 비율이 91.5 → 97.8 %로 올랐다.
  - 두 commit 사이 코드는 수집을 바꾸지 않는다(사전확률 층과 정답 스크립트가 남기는 열만 다름). 그래서 이 차이는 그날 아카이브 상태에서 온 것이다.
  - 천체별 기록은 프로토콜(규칙 2)상 남기지 않으므로 더 추적하지 않았다.
- **이 숫자로 아무것도 고치지 않는다(규칙 3).** 떨어진 것도 아니어서 따로 조사할 것은 없다.

### 왜 이렇게 했나
- **관문을 그대로 두었다.** 시도 1은 시작 전 상태 검사(3′ 원뿔)가 정상 속도(5.7 s)였는데도, 60개 영역 12′ 질의를 20개씩 동시에 보내는 도중 40 %가 시간 초과됐다. 그러니 상태 검사의 응답 시간으로 출발을 막는 문턱을 더해도 이런 경우를 걸러내지 못한다. 반면 채점 직전 관문(영역별 수집 요약)은 실제 수집 결과를 보므로, 두 번 모두 기회를 쓰기 전에 멈췄다. 그래서 관문은 바꾸지 않고, 상태 검사로 회복을 확인한 뒤 같은 실행을 처음부터 다시 돌렸다(60개 영역 수집 포함 63개 작업 모두; 실패한 작업만 다시 돌리면 장애 때 모은 영역 자료가 그대로 남는다).
- **PATCH로 올렸다.** 점수 기록은 분류 결과를 바꾸지 않는다. 2.51.0 점수를 2.51.2(PATCH)로 기록한 선례를 따랐다.
- **2.53.0과 2.53.1은 채점하지 않는다.** 2.52.0 이후 `v2/Preprocess`(1차 분류 코드)는 바뀌지 않았다. 2.53.x는 세부 분류와 검증 입력만 바꿨다. 세트 C는 1차 분류만 채점하므로, 같은 숫자를 얻으려고 기회를 쓸 이유가 없다. 다음 채점은 1차 분류가 바뀌는 판에서 한다.
